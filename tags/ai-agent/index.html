AI Agent 到底怎麼運作？用 Antigravity 圖解 Claude 的工具調用機制

延續前篇探討的「多帳號開發工作流」，你可能會好奇：如果我特別偏愛 Claude 的程式碼風格，難道只能在網頁版來回複製貼上，或是開著 Claude 桌面版（Desktop）與編輯器在兩個 App 之間頻繁切換操作嗎？能不能讓 Claude 直接且無縫地操控我的本機開發環境？ 答案是肯定的！本文將帶你一窺現代 AI 開發環境的底層機制，圖解如何將「最聰明的 AI 大腦」完美封裝進「安全的本機執行框架」中。 一、 抽換大腦：當 Antigravity 遇上 Claude 在 Antigravity 這樣的 Agent 平臺系統中，我們可以隨時從介面上切換驅動系統的大語言模型（LLM）。當我們在選單中選擇 Claude Sonnet 4.6 時，發生了什麼事？ 簡單來說：Antigravity 提供了「手與腳（操作本機的工具與權限）」，而 Claude 則成為了「大腦（思考邏輯與決策）」。 這種結合帶來了極大的優勢： 無縫結合：我們的每一個指令都會直接送給 Claude 思考，再由 Claude 控制 Antigravity 的工具來幫我們寫本機檔案。 無雙重消耗：這是一次性的 API 請求，完全不會浪費 Token，只會消耗系統中該模型對應的配額，也就是說，我們不需要先讓某個模型做初步規劃，再手動把結論丟給另一個模型實作、讓它重新瞭解情境；在這裡，我們可以直接順著脈絡接續進行。 依任務彈性調整：它的優勢是可以藉由這個平臺，隨著任務調整我們想要的模型。也就是說，不會先從 Gemini 解析我們的要求，然後才發現要再調用 Claude Sonnet 進行任務。 二、 一張圖看懂 Agent 的運作流程 為了讓這個概念更具象化，我們來看看當我們輸入「請幫我建立一份 README.md」時，底層到底發生了什麼事： sequenceDiagram actor User as 開發者 (我們) participant IDE as Antigravity 框架/工具箱 participant Brain as AI 大腦 (Claude Sonnet) participant OS as 本機作業系統 User->>IDE: 1. 任務：「請幫我建立一份 README.md」 IDE->>Brain: 2. 傳送文字與可用工具清單 (如 write_to_file) Note over Brain: 思考中：了解需求，決定調用工具 Brain-->>IDE: 3. 回覆：「我要呼叫 write_to_file 工具」 alt 需要權限授權 IDE->>User: 4. 畫面彈出：「Claude 請求寫入檔案，是否同意？」 User-->>IDE: 5. 點擊「同意 (Proceed)」 end IDE->>OS: 6. 執行寫入動作 (創造實體檔案) OS-->>IDE: 7. 檔案建立成功 IDE->>Brain: 8. 回報：「檔案已成功建立」 Brain-->>IDE: 9. 總結：「我已經為我們建立好檔案了！」 IDE->>User: 10. 將最終結果顯示在對話視窗中 從上圖可以清楚看到，AI 大腦（Claude）並沒有能力直接竄改我們的電腦，它必須向框架提出「請求」，而最終的生殺大權（授權）始終掌握在我們手中。這是目前最安全也最高效的協作模式。 ...

一人團隊的 AI 協作術：如何打造公私分明的 AI 開發工作流

在當今 AI 爆發的時代，身為一個「一人開發團隊」，如何善用各種 AI 工具加速專案開發，同時又能兼顧帳號額度效率與公司智慧財產權 (IP) 安全？ 這篇文章將分享我近期整理出的一套開發工作流，探討如何將 Claude、Antigravity (AI Agent & IDE) 以及 Obsidian 串聯起來，打造出極致且「公私分明」的開發體驗。 一、 釐清概念：AI Agent 與 AI IDE 的區別 許多人在剛接觸這些工具（例如新興的 AI 開發神器 Antigravity）時會感到困惑：「AI 助理（如 Antigravity Agent）和 AI 編輯器（如 Antigravity IDE）有什麼不同？只差在能不能在視窗裡看程式碼嗎？」 其實，兩者的角色定位截然不同： AI Agent（大腦）：它是負責思考與執行的主體。即使你不在特定的 IDE 內，它依然能透過工具讀取你的本機專案、在程式碼中搜尋關鍵字、直接修改檔案，甚至在你的授權下執行本機終端機指令（如 npm install、git push）。 AI IDE（辦公桌）：它是給開發者（你）使用的視覺化介面。它將 Agent 寫好的程式碼即時呈現出來，讓你方便檢視檔案樹、進行語法高亮、手動微調，並提供網頁的即時預覽功能。 二、 多帳號環境下的「公私分明」工具鏈規劃 當我們同時擁有「公司帳號（通常為免費或入門方案）」與「個人帳號（如 Google AI Pro 等高級方案）」時，如果把私人的高級額度拿去跑公司專案，除了很快會把額度耗盡外，也會產生智財權與合規的灰色地帶。 因此，規劃出一套能發揮各家 AI 專長，且帳號界線分明的雙軌開發工具鏈，是現代開發者的必修課： 👤 軌道一：個人開發軌（使用個人 Pro / API 方案） 主力工具： Antigravity CLI/網頁版（綁定個人 Pro 帳號）：享受無限制的額度與強大模型，用來跑自己 Side Project 的專案初始化、程式碼生成與本機測試。 VS Code (搭配個人 API Key)：作為日常寫扣與微調的編輯器。 Obsidian (搭配 Gemini API Key)：作為本地知識庫，整理開發筆記、進行知識萃取與架構發想。 核心目的：最大化個人 Pro 方案價值，專注於個人技術積累與 Side Projects 的敏捷開發。 🏢 軌道二：公司開發軌（使用公司授權/免費額度） 主力工具： Claude Desktop / Claude Code CLI（公司帳號）：負責高層次架構規劃、PRD（產品需求文件）撰寫與主要代碼設計。Claude 極佳的語意邏輯在這邊能發揮最大效益。 Antigravity IDE（公司 Starter 帳號）：只用作輔助性的微調、簡單 Bug 排查，或者根本不使用。 核心目的：確保公司專案的程式碼留在公司授權的管道中。如果未來公司專案非常需要強大的本地 Agent 協作，應向公司申請企業授權，而非使用個人帳號頂替。 三、 給一人團隊的實戰建議 透過上述的工具分工，一人團隊也能展現出極高的戰鬥力： ...

AI 不是來搶飯碗，讓自己從「養馬人」到「開車者」

近期在公司的 AI 聚會中，不時會聽到大家對於應用 AI 技術的興奮與期待。然而，擁抱新科技同時，面對 AI 的強勢崛起，大家不免在會議中提問到：我們到底該如何善用它？而我們未來的職涯又將會變成什麼模樣？ AI 時代的衝擊與省思 剛開始接觸 AI 的時候，我覺得它就像個很聰明的實習生，你問一句它答一句，不推就不會動。但隨著這兩年技術爆發，今年初我開始將注意力放在 AI Agent，投入了大量時間學習如何使用它。實作一陣子後，深深覺得其能力令人驚艷，現在 AI 帶來的生產力提升，我真的能實現傳聞中「10 倍工程師」的效益（雖然我目前連一半都還沒達到）！ 然而，越是深入研究，越是感到迷惘：我的存在價值會不會就此被 AI 取代？雖然目前臺灣的軟體界還未受到強烈衝擊，畢竟就現實面的成本考量而言： 矽谷軟體工程師 > AI Token > 臺灣軟體工程師 但在國外，許多人已選擇離開受到 AI 浪潮衝擊劇烈的美國，回到臺灣發展。這波由 AI 引起的產業結構改變與裁員潮，也讓我開始警惕。如果等到衝擊真正襲來才開始尋求轉型，恐怕為時已晚。 因此，這段時間除了持續學習 AI 技術外，我也開始廣泛閱讀，試圖了解軟體工程師（或是稱「人」）在 AI 時代的生存之道。在這個過程中，我接觸到了「HITL (Human-in-the-loop，人機協作)」的概念。 HITL 的核心精神是在 AI 執行任務的過程中，仍需要人類來檢視、回饋與下達關鍵判斷。講白一點，HITL 就是 AI 幫你做事，但最後背鍋的人還是你，畢竟晚上被吵醒會生氣的不是 AI，是我們自己。所以與其抗拒，不如把 AI 當成隨傳隨到的助理，結合自己的 domain know-how，把它用好用滿！ 人並未消失，而是轉換了角色與位置 我曾在 AI 聚會中與夥伴們分享過一個比喻：現在我們面對 AI 工具的衝擊，就像是馬車時代的人們遇見了汽車。 在馬車時代，出遠門需要馬伕，旅途中至少要有兩個人與一匹馬。當汽車出現後，我們不再需要馬伕了，自己就能決定目的地。這不僅省去了聘用與溝通成本，旅途時間也變得更加彈性，不再需要遷就馬伕的作息或馬匹的體力。我們只需獨自握住方向盤，就能隨時出發（當時有夥伴打趣地說：現在不都是自動駕駛了嗎XD）。 使用 AI 也是如此，我們可以隨時呼叫 AI 助理群，不用擔心它們是否需要休息或休假，隨時都能上工（自己扮演慣老闆）。 然而在這個過程中，「人」依然是不可或缺的。過去可能需要一個團隊才能完成的任務，現在或許靠自己加上 AI 就能搞定。但關鍵在於，你必須決定方向、規劃路線，這些核心決策是無可取代的。 改變的只是所需的技能門檻：過去我們需要了解馬的習性，現在我們不需要精通汽車的每一個機械結構，就能享受更便利、更高效的移動方式。因此，人類並未在 AI 發展的過程中被淘汰，而是我們的職責與定位進行轉換。 我們不會消失，會成為設計與修車的人 在現代，AI 能協助沒有程式背景的人輕鬆開發出全新的系統。然而，當這些系統需要進行複雜的架構調整或深度改版時，還是會遇到瓶頸。這正是軟體工程師發揮價值的時刻，我們將成為帶領 AI 助理與小工程師們進行系統升級的架構師。 ...
